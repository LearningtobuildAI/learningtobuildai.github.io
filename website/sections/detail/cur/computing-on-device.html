PART 1Executive Overview
1Definition

Computing on device refers to the capability of running artificial intelligence (AI) models locally on a device rather than sending data to a remote server for processing.

Category

2Problem It Solves

It addresses the challenges of high latency in real-time applications and excessive power consumption when transmitting large amounts of data to remote servers for processing.

PART 2Technical & Manufacturing
4How It Works

This technology allows AI models to run directly on the hardware of a device, such as smartphones or IoT devices, by optimizing the model's architecture and using specialized hardware accelerators. This minimizes latency and power consumption compared to cloud-based solutions where data must be transmitted over networks.

5Materials Used
  • silicon
  • accelerators
  • AI models
6Manufacturing / Creation Process

The manufacturing process involves optimizing existing hardware or designing new specialized hardware accelerators that can efficiently run AI models. This includes integrating these accelerators into devices like smartphones, tablets, and IoT gadgets.

7Build Process

Building computing on device solutions requires expertise in both software and hardware engineering. It involves model optimization techniques such as quantization, pruning, and knowledge distillation to reduce the computational requirements of AI models. Hardware design focuses on creating efficient silicon that can handle these optimized models without significant power draw.

PART 3Engineering & Build Guide

9Engineering Breakdown
  • Compressed model — the neural network itself, shrunk to fit a phone's memory and power budget. Key parts: weights reduced to 8-bit or 4-bit integers, pruned and distilled network, task-specific layers.
  • Compute accelerator — runs the matrix maths without draining the battery. Key parts: neural processing unit (NPU), GPU and digital signal processor, matrix-multiply and activation units.
  • Memory system — feeds a compute engine that is starved of bandwidth long before it runs out of arithmetic. Key parts: on-chip SRAM buffers, shared LPDDR memory, weight streaming.
  • Runtime and compiler — turns a trained model into a schedule of operations the chip can execute. Key parts: graph optimiser, operator fusion and kernel selection, scheduler and memory planner.
  • Storage and update layer — stores model files and replaces them without breaking the device. Key parts: flash storage, over-the-air model updates, versioning and rollback.
  • Power and thermal manager — keeps sustained performance from collapsing into throttling. Key parts: dynamic voltage and frequency scaling, thermal sensors, workload batching.
10How It's Made — Step by Step
  1. Train the model. Large datasets and many accelerators produce an accurate but oversized network in a data centre.
  2. Compress it. Pruning removes near-useless connections, distillation trains a smaller student network, and quantization maps floating-point weights onto 8-bit or 4-bit integers.
  3. Compile for the target chip. The runtime fuses operations, chooses kernels written for that NPU or GPU, and plans how tensors move between memory tiers.
  4. Bind it into the application. The model file ships inside an app or operating system, called through a framework API rather than a network request.
  5. Validate on real hardware. Accuracy, latency, memory footprint and battery drain are measured on the actual devices and chips being targeted.
  6. Ship and version. The model is delivered in an app update or operating system release, with fallbacks for older hardware.
  7. Run in production. Inference happens locally; telemetry (where privacy permits) reports crashes and latency rather than sending user data away.
  8. Improve from the field. Curated samples or on-device learning loops feed a retrained model back into the next release.
11Prerequisite Technologies
  • EXISTS Low-power parallel silicon (NPUs) — general-purpose CPUs cannot run modern neural networks at acceptable speed per watt.
  • EXISTS Model compression and quantization tooling — without 4–8 bit integer weights, most models simply do not fit in device memory.
  • EXISTS Efficient neural architectures — compact transformer and convolutional designs set the ceiling on what a device can run.
  • PARTIAL Mature ML compiler stacks — each accelerator vendor still needs its own kernels and toolchain, so models are not portable for free.
  • PARTIAL On-device training and federated learning — personalisation without sending raw data to a server is demonstrated but not routine.
12Where It Goes Next
  1. Now: speech recognition, translation, photo processing and small vision models running locally on phones and laptops — instant, private, offline features.
  2. Next: billion-parameter language models running on flagship phones and PCs — assistants that keep working with no connectivity.
  3. Next: on-device personalisation and federated training at scale — models that adapt to one user without their data leaving the device.
  4. Longer term: always-on local agents coordinating several models across a device's chips — a shift of routine inference from data centres to the edge, cutting latency and energy.
