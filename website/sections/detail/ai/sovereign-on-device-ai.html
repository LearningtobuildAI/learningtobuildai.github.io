PART 1Executive Overview
1Definition

Sovereign On-Device AI refers to the implementation of artificial intelligence models, specifically large language models (LLMs), directly on end-user devices. This technology utilizes high-bandwidth memory and neural processing units (NPUs) integrated into the device hardware for local computation and inference.

PART 3Engineering & Build Guide

9Engineering Breakdown
  • Compute engine — runs the neural network's matrix multiplications locally. Key parts: NPU with INT8/INT4 datapaths, GPU shaders for large batches, CPU fallback for odd shapes.
  • Memory subsystem — feeds weights to the compute units fast enough to generate tokens. Key parts: on-package LPDDR5X, unified memory controller shared by CPU, GPU and NPU, large last-level cache.
  • Quantized model format — stores weights in 4-bit so a multi-billion-parameter model fits in device memory. Key parts: grouped weight blocks, per-group scale and zero-point, embedding and output layers kept at higher precision.
  • Runtime and compiler — maps the model graph onto the available engines. Key parts: graph compiler and operator fusion, kernel library, KV-cache manager, weight paging or streaming.
  • Power and thermal control — keeps sustained token rate inside the device's power budget. Key parts: DVFS and clock gating, skin-temperature sensors, throttling governor.
  • Privacy and security layer — keeps prompts, context and personal data on the device. Key parts: secure enclave for keys and model decryption, sandboxed model storage, optional local retrieval index.
10How It's Made — Step by Step
  1. Design the system-on-chip. The NPU, memory controller and cache hierarchy are laid out together, because moving weights costs far more energy than multiplying them.
  2. Attach the memory. LPDDR5X dies are packaged close to or stacked with the SoC to raise bandwidth and cut the energy per bit moved.
  3. Quantize the model. A trained model is converted to 4-bit weights with per-group scaling, calibrated on sample data to limit accuracy loss; activations often stay at 8 or 16 bits.
  4. Compile to the accelerator. The runtime fuses operators, picks tiling and memory layouts, and decides which layers run on the NPU, GPU or CPU.
  5. Plan memory. Weight buffers and the KV cache are laid out in the unified pool; long contexts are paged or streamed from flash when they exceed capacity.
  6. Tune the scheduler. Weight prefetching, compute overlap and speculative decoding are tuned so the memory bus stays busy while power stays under budget.
  7. Validate thermally. Sustained tokens per second are measured over minutes, not seconds, to set the real clock and throttle profile.
  8. Ship signed model packages. Models and updates are encrypted, signed and delivered into sandboxed storage that the runtime can load without exposing user data.
11Prerequisite Technologies
  • EXISTS LPDDR5X and on-package memory — token generation is bandwidth-bound: every generated token reads all the weights once.
  • EXISTS INT4/INT8 weight quantization — it cuts a 7-billion-parameter model to roughly 3–4 GB so it fits in device memory.
  • EXISTS NPUs in consumer silicon — they deliver useful matrix throughput at a few watts.
  • PARTIAL Mature cross-vendor runtime tooling — models must still be recompiled for each vendor's accelerator, which slows porting and optimisation.
  • PARTIAL Large unified memory pools (32 GB and up) — bigger models need capacity, not just speed, and that is only now reaching laptops and tablets.
  • PARTIAL Sustained thermal headroom — phones throttle within minutes, so long generations and long contexts degrade.
12Where It Goes Next
  1. Now: 7–8-billion-parameter models running at a few to tens of tokens per second on phones and laptops — private assistants that work offline with no data leaving the device.
  2. Next: 30-billion-parameter and mixture-of-experts models on 32–64 GB unified-memory laptops — near-cloud quality for drafting, coding and summarising without a network.
  3. Next: on-device multimodal models and agents that call local tools — voice, camera and document workflows handled entirely locally.
  4. Longer term: on-device personalisation and fine-tuning, with only aggregated updates leaving the device — models adapted to one user's data without that data ever being centralised.
