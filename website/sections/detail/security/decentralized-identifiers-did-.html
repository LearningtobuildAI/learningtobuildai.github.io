9Engineering Breakdown
  • DID method — defines one flavour of DID and the rules for creating, resolving, updating and deactivating it. Key parts: method name (e.g. did:web, did:ion), lifecycle operations, method specification.
  • DID document — the machine-readable record a verifier fetches: public keys, verification methods and service endpoints. Key parts: verification method entries, authentication and assertion keys, service endpoints.
  • Verifiable data registry — the shared source of truth that anchors DIDs, replacing a central authority. Key parts: distributed ledger or web domain, anchor/batch mechanism, method-specific resolver driver.
  • Wallet or agent — holds the controller's private keys and signs on their behalf. Key parts: secure key storage (secure enclave or HSM), key rotation and recovery, credential store.
  • Credential layer — the actual statements being proven — a degree, a licence, an employment claim. Key parts: issuer signing, verifiable credential and presentation, status/revocation list.
  • Resolution layer — turns any DID string into its current document, whatever method it uses. Key parts: universal resolver, resolver drivers, caching and validation.
10How It Would Be Made — Step by Step
  1. Pick or define a DID method. Choose an existing method such as did:web or did:ion, or write a specification naming the registry, the DID syntax and the operations allowed on it.
  2. Generate keys in the wallet. The controller's device or hardware module creates a key pair; the private half never leaves secure storage.
  3. Compose the DID document. Public keys, verification methods and service endpoints are assembled into the document the method expects.
  4. Anchor it in the registry. The document is published — to a ledger, a batch anchor, or a web domain's well-known path — establishing a root of trust.
  5. Resolve the DID. A resolver reads the DID string, routes to the right method driver, fetches and validates the current document.
  6. Issue a verifiable credential. An issuer signs a set of claims with its own DID key and hands the credential to the holder's wallet.
  7. Present and verify. The holder builds a presentation, optionally disclosing only some fields; the verifier resolves the issuer's DID and checks the signature and status.
  8. Rotate, recover and revoke. Keys are rotated or the DID deactivated, and issued credentials are checked against a revocation list so stale ones fail.
11Prerequisite Technologies
  • EXISTS Public-key cryptography — every DID is just a key pair plus a way to publish the public half; Edwards-curve and elliptic-curve signatures do the work.
  • PARTIAL Tamper-evident registries — a DID needs somewhere to anchor that no single party can silently rewrite — a ledger, or a domain the controller genuinely controls.
  • EXISTS Secure key storage — self-sovereignty is worthless if the private key can be copied off the device.
  • EXISTS Standardised data models and resolution — W3C DID Core 1.0 became a Recommendation in July 2022, alongside the verifiable-credentials data model, so independent systems can interoperate.
  • PARTIAL Selective disclosure and revocation — holders need to prove one attribute without revealing the rest, and verifiers need to know a credential has not been withdrawn.
12Path to Full Scale
  1. Now: W3C-standardised DIDs and verifiable credentials in enterprise and wallet products — credentials that a verifier can check cryptographically instead of phoning the issuer.
  2. Next: national and regional digital identity wallets built on these standards, such as the EU Digital Identity Wallet programme under eIDAS 2.0 — government-issued identity that citizens hold themselves and reuse across borders.
  3. Next: cross-method interoperability, so a wallet holding any DID can present to any verifier — networks where issuers and verifiers never need a shared platform.
  4. Longer term: DIDs built into browsers and operating systems as an ordinary login — sign-in without passwords or per-site accounts, with the user holding the keys.
